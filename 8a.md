# Этап 8 — Кейсы (профильные группы учеников)

## Context

Обратная связь заказчика: кроме классов в школе есть **кейсы** — кружки профильной
деятельности, где ученики из РАЗНЫХ классов занимаются под руководством 2–3 учителей.
Нейминг «кейс» — школьный, используем его как есть.

Что требуется:
1. Кейс как сущность: состав учеников + учителя, учителей можно добавлять к
   существующему кейсу.
2. При запуске кампании админ выбирает не только классы, но и кейсы.
3. Ученик, попавший в кампанию и через класс, и через кейс, заполняет **одну**
   самооценку.

Уточнено с заказчиком:
- Ученик состоит **ровно в одном** кейсе; учитель ведёт **ровно один** кейс.
- Кейс **разновозрастный** — ученики из разных классов.
- Через кейс ученика оценивают **самооценка + учителя кейса** (родителей кейс
  не добавляет; они приходят только из класса, если класс тоже в кампании).
- Учителя кейса **видят индивидуальные результаты** учеников своего кейса.
- Аналитика по кейсу — **полный аналог класса**: средний профиль, зоны роста,
  ростер учеников, покрытие анкетами.

Важное следствие из текущего кода: «одна самооценка» получается **бесплатно** —
`merge_pairs` схлопывает пары по `(respondent_id, subject_id)`, а
`UniqueConstraint(campaign_id, respondent_id, subject_id)` на `Assessment`
страхует на уровне БД. Пара `(s, s)` из класса и из кейса — одна и та же пара.
Слои же складываются: учителя класса и учителя кейса дают каждый свою анкету.

## 8a — Модель и CRUD кейсов (бэкенд)

Новый модуль `vektor-backend/src/vektor/modules/cases/` по образцу
[classes/](vektor-backend/src/vektor/modules/classes/).

**Модель** (`cases/models.py`), одна миграция поверх head `e7b3f9c2a815`:
- Таблица `cases`: `id`, `name: String(255)` (UniqueConstraint), `description: str|None`,
  `created_at`.
- `users.case_id: int|None → cases.id` — **одна колонка на обе роли**, потому что
  и ученик, и учитель состоят ровно в одном кейсе. Это прямой аналог
  `users.school_class_id`, а не M2M: «один» — требование заказчика, и FK выражает
  его схемой, а не проверкой в сервисе.
- `assessments.subject_case_id: int|None → cases.id` — снапшот кейса субъекта на
  момент генерации, ровно по тем же мотивам, что `subject_class_id` (перевод
  ученика между кейсами не должен переписывать прошлогоднюю аналитику).

Relationship-проекции на `Case` — тем же приёмом, что `SchoolClass.homeroom_teachers`
(строковые primaryjoin, `viewonly=True`, `User` импортирован только под
`TYPE_CHECKING`):
- `members` — пишущая сторона (`back_populates` на `User.case`);
- `students` / `teachers` — viewonly-проекции с условием на `User.role`.

**Сервис/роутер** (`/cases`, всё под `require_role(ADMIN)`, кроме списка — он же
доступен `TEACHER`, как `GET /classes`):

| метод | путь | смысл |
|---|---|---|
| POST | `/cases` | создать |
| GET | `/cases` | список с составом |
| PATCH | `/cases/{id}` | переименовать / описание |
| POST | `/cases/{id}/students` | bulk-привязка (как `assign_students`) |
| POST | `/cases/{id}/teachers` | bulk-привязка |
| DELETE | `/cases/{id}/students/{sid}` | открепить |
| DELETE | `/cases/{id}/teachers/{tid}` | открепить |
| DELETE | `/cases/{id}` | удалить (только пустой) |

Доменные ошибки в стиле `classes/service.py` (наследники `DomainError`, роутер их
не ловит — см. Этап 7a): `CaseNotFound(404)`, `CaseAlreadyExists(409)`,
`WrongRole(409)`, `AlreadyInAnotherCase(409)`, `NotInCase(404)`, `CaseNotEmpty(409)`.
`AlreadyInAnotherCase` намеренно — молчаливый перенос из чужого кейса скрыл бы
ошибку админа; перевод = сначала DELETE, потом POST.

Верхней границы «2–3 учителя» на бэкенде **нет** — это практика школы, а не
инвариант данных (то же решение, что для 2–4 учителей в 7o). Предупреждает UI.

Кандидаты в состав фильтруются по `is_active` — иначе в списки попадут служебные
респонденты архивного импорта (`is_placeholder`), находка 7m.

Грабля из 7m, повторить: `_load_case` должен идти с
`execution_options(populate_existing=True)` — сессия живёт с
`expire_on_commit=False`, иначе ответ вернёт состав ДО изменения.

## 8b — Кейсы в генерации кампании

Файл: [assessments/service.py](vektor-backend/src/vektor/modules/assessments/service.py#L343)

- `GenerateIn` (`assessments/schemas.py`): `class_ids` теряет `min_length=1`,
  добавляется `case_ids: list[int] = []`; валидатор модели требует, чтобы хотя бы
  один из двух списков был непуст (кампания может идти только по кейсам).
- `generate_assessments(...)` получает `case_ids: list[int] | None = None`.
  **`build_pairs` не трогаем вообще**: кейс — это вызов
  `build_pairs(student_ids, parent_ids_by_student={}, teacher_ids=case_teacher_ids,
  include_peers=False)`, что по её же правилам даёт ровно «самооценка + учителя».
  Результат вливается тем же `merge_pairs` — там и схлопывается общая самооценка.
- Поштучного выбора учителей кейса (аналога `teacher_ids_by_class`) **не делаем**:
  в кейсе их 2–3 по определению, и все они ведут профильную деятельность. Берём
  всех учителей кейса.
- Снапшоты: рядом с `class_id_by_subject` собирается `case_id_by_subject`.
  Обе колонки заполняются **по членству субъекта**, а не по происхождению пары:
  если ученик и в классе, и в кейсе кампании, у всех его анкет проставлены обе.
  Иначе покрытие кейса не показывало бы, что ученик уже отдал самооценку в классе.

## 8c — Аналитика по кейсу (results)

Файл: [results/service.py](vektor-backend/src/vektor/modules/results/service.py)

**Права** (чистые функции, строки ~233–265):
- `can_view_results(...)` получает параметр `case_teacher_ids: set[int]`; учитель
  кейса приравнивается к учителю класса.
- Новая `can_view_case_results(user_id, role, case_teacher_ids)` — зеркало
  `can_view_class_results`.
- `_load_subject_for_results` (~стр. 390) дополняется
  `selectinload(User.case).selectinload(Case.teachers)`.
  Права, как и раньше, считаются по **текущим** связям, а агрегация — по
  зафиксированным `rater_role`/снапшотам.

**Переиспользование вместо копирования.** `get_class_results` (стр. 817) после
получения `class_subject_ids` не содержит ничего классового: сравнение со школой
за период, `average_profiles`, `count_growth_zone_hits`, `rank_growth_zones_by_hits`.
Выносим этот хвост в приватную `_group_profile(db, campaign, subject_ids) -> dict`
и делаем `get_class_results` / `get_case_results` тонкими обёртками, которые
добавляют свои `class_id`/`class_label` либо `case_id`/`case_name`. Так же
поступаем с `get_class_roster` (стр. 1141): «состав = снапшот кампании ∪ текущий
состав группы» — общая логика, различаются источник состава и проверка прав.

Новые эндпоинты в `results/router.py` (литеральные маршруты — ДО `/{subject_id}`,
как уже сделано для `class/`):
- `GET /results/case/{case_id}?campaign_id=` → профиль кейса
- `GET /results/case/{case_id}/roster?campaign_id=` → ростер (`only_completed=False`)
- `latest_campaign_id_for_case` — копия `latest_campaign_id_for_class` (стр. 734)
  по `Assessment.subject_case_id`.

**Покрытие.** `get_campaign_coverage` (стр. 906) получает вторую секцию `cases`:
та же группировка, но по `subject_case_id`, плюс `_campaign_students_by_case` по
образцу `_campaign_students_by_class` (стр. 971). Это **второй независимый разрез
тех же анкет**, а не слагаемое: `total`/`completed` в шапке остаются по анкетам
кампании целиком, суммы по классам и по кейсам пересекаются. Обязательно
отразить в UI подписью, иначе цифры прочтутся как складывающиеся.
